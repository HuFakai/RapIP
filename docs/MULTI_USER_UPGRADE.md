# 多用户升级方案

更新日期：2026-11-05。性质：未来规划，不属于首版交付，不要求提前实现全部预留。首版已包含单管理员页面、React Bits 视觉方向与长连接管理，不等于多用户系统；当前行为以 [SPEC.md](../SPEC.md) 为准。

## 1. 升级目标

在自用网关上增加独立用户身份、会话、资源权限、配额与审计，继续保证独占、冷却、恢复和连接撤销，不将一个用户已用的 IP 当作其他用户的新 IP。

多用户和多实例是两个阶段；先保持单调度所有者，不因增加用户立即引入分布式一致性。

## 2. 首版最低预留

- 使用内部 principal_id，展示用户名不是数据库身份。
- worker、session、控制操作和幂等键带主体命名空间。
- 稳定 binding_id、node_id、generation、account_id，不只按 session 字符串控制。
- 协议与 HTTP handler 经统一调度层，不直接改节点或写状态表。
- 认证抽象为主体上下文，首版管理员与业务凭据映射到固定 owner，不做多用户注册与权限面板。
- 凭据、配置与业务状态分开，数据库有 schema 版本与迁移入口。
- 隧道有流量统计接口，首版仅诊断，不称作计费账本。
- 数据访问封装在存储模块，不要求通用 ORM 或插件框架。

## 3. 阶段一：单实例多用户

### 3.1 身份和权限

增加用户、凭据和角色，支持轮换、禁用，分离管理 Token 和业务凭据。认证后查询资源权限，不能由路由参数指定别人的主体。

绑定、查询、释放和操作状态按主体过滤；跨用户管理需独立权限与审计。沿用首版建议的 FastAPI/OpenAPI 和 React 页面，增加用户视图与角色能力。后端仍执行全部授权，前端隐藏菜单不构成权限隔离。

长连接统计和控制必须按主体、绑定与 generation 隔离；用户不能看到或关闭其他人的排空隧道。保留 session 的手动轮换与自动故障转移同样消耗所属用户预算。

### 3.2 资源模式

| 模式 | 归属 | 适用情况 |
| --- | --- | --- |
| 共享热备池 | 共享未用库存，绑定期间严格独占 | 利用率优先 |
| 用户专属池 | 指定账号/资源只供一个用户 | 预算和资源隔离 |

两者均跨账号去重，同一运营池的冷却跨用户生效。用户响应不泄漏其他人的 IP、session、用量和账号凭据。

### 3.3 配额与公平

至少支持每用户活跃绑定、并发隧道、换号速率、替换预算和国家权限，匿名 session 同样受限。共享池按用户公平排队，限制突发，资源不足不抢占其他人的连接。

区分业务换号、节点故障、碰撞重抽和重启损耗，明确哪些计入用户预算。供应商流量与网关字节口径可能不同，不能承诺天然一致。

### 3.4 账本、存储和审计

增加追加式用量事件和操作日志。正式计费另设计结算、对账、补偿与争议查询，不直接按可变累计计数收费。

单实例低写入量可留 SQLite；多管理进程、复杂报表或多客户端事务需求出现时再迁移 PostgreSQL，重新验证约束和事务。

## 4. 阶段二：控制与转发分离

独立管理、部署或扩展需求出现后拆分：

- 控制面：身份、授权、配额、配置、管理 API、账本与审计。
- 网关执行器：握手、桥接、隧道、绑定和节点操作。
- 补货执行器：供应商任务和对账，有明确账号所有权。

命令经认证，带幂等键、预期 generation 和查询结果；API 不绕过所有者直接改数据库状态。

PostgreSQL 可作事实源；Redis 仅按实际缓存、通知或限流需求引入，不默认作唯一事实源。通信协议到该阶段再选。

## 5. 阶段三：多网关

先按账号分片，一个账号的同步、分配与替换由一个所有者负责，共享主体配额和物理 IP 冷却。

必须补充：

- 所有者租约与单调 fencing token，拒绝过期所有者分配。
- 跨分片原子的物理 IP 占用与冷却准入，不能只本地去重。
- 会话稳定路由或目录，跨分片国家筛选和公平调度。
- 外部 Replace API 不接受本地 fencing token 时，以唯一受控执行入口、任务认领和对账防双写，不能声称数据库锁可撤销已发出的请求。
- 失败实例的 TCP 不可迁移，客户端重建；是否保留原 IP 另做租约策略。

先验证单实例接近实际瓶颈，再进入此阶段，不只因 IP 数增加而拆分。

## 6. 迁移与验收

1. 固定 owner 映射为管理员，保留历史主体 ID。
2. 上线用户、凭据与授权，验证相同 worker/session 在不同用户互不影响。
3. 增加配额和公平队列，避免单用户耗尽资源或无限消耗替换预算。
4. 上线用量与审计，验证备份、恢复、禁用和凭据轮换。
5. 必要时再迁移数据库、拆控制面、引入分片，各步独立验收。

验收包括跨用户访问拒绝、全局不撞 IP、预算原子扣减与回补、禁用阻止新连接、操作幂等、所有者故障恢复、日志不暴露凭据。

## 7. 未来重新确认

是否商业化、共享池或专属池、账号由谁持有、并发用户、流量口径、数据保留与可用性目标。现阶段不把这些未决事项硬编码到自用版。
